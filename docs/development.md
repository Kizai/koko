# Koko 开发规则

[返回文档目录](./README.md)

本文件适用于整个仓库。[架构设计](./architecture.md)记录系统目标，[实现计划](./implementation.md)记录当前交付范围和验收顺序。

## 先确定问题和方案

1. 从可观察的行为、期望结果和现有约束出发，追溯根因。判断提议中的问题定义是否把症状当成原因、把手段当成目标。发现更值得解决的问题时，直接指出并给出依据。
2. 有会改变范围、接口或验收方式的歧义时，先问清用户偏好。对齐后给出三种有实质差异的方案，说明各自的成本、适用条件和验收方式。
3. 对设计变更推演二阶和三阶影响，覆盖上下游模块、用户操作、系统复杂度和长期维护。考虑其他领域的成熟做法，并用最强反例或边界条件检验首选方案。记录什么证据会使方案改变。
4. 改动已有设计前，查阅相关提交、关键 PR 和架构演变。识别有意保留的约束、历史兼容和已失效的前提，根据调用方和验证证据判断旧设计能否移除。
5. 评估第一次接手项目的人能否沿入口找到主流程。发现命名歧义、职责重叠或理解成本高的抽象时，优先简化当前改动涉及的部分。

## 实现约定

- 防御性代码要有明确依据。缺乏证据或概率极低的异常直接记录观察条件即可。确有必要额外防御时，先说明发生条件、证据、改动成本和维护成本，得到用户同意后再写。按已约定的协议和授权要求实现入口校验及权限检查。
- 每处外部输入在进入对应信任边界时校验一次，并转换成内部类型。内部流转复用类型表达的约束。涉及随请求或时间变化的授权、能力和租约时，由主机在执行边界判定。
- 一次性且简单的逻辑就地书写。抽取函数要有真实复用、足够复杂的逻辑，或能把完整的入口校验从主流程中移出。入口函数保留读取配置、调用主要步骤和汇报结果的顺序。
- 注释解释难以从代码读出的约束、平台差异和取舍。能通过命名和类型表达的内容用代码表达。
- 生成产物统一从源头更新。AI 生成文件变更时，修改源提示词或生成输入，再按原流程重新生成。用 Cargo 更新 `Cargo.lock`，用各自的生成工具更新其他生成产物。
- 沿用仓库已有的工具和惯例。测试优先运行真实协议、真实文件路径和实际入口。外部条件难以在自动化环境复现时，用最少的替身覆盖必要分支，并保留实机验收。

## 验证与复盘

- 先验证受影响的 crate 和入口。Rust 改动完成后执行以下工作区检查，并按实现计划验证相应实机场景。

  ```bash
  cargo fmt --all -- --check
  cargo clippy --workspace --all-targets --locked -- -D warnings
  cargo test --workspace --locked
  ```

- 提交评审材料时写明目标、改动、验收结果和仍需实机验证的场景。涉及接口、配置或阶段边界时同步更新相关文档。
- 项目文档统一放在 `docs/`。维护长期文档时同步更新[文档目录](./README.md)，需要自动清理的短期笔记按[到期规则](./README.md#临时笔记)管理。
- 做 PR 效率复盘时，先确定时间窗口与耗时口径，再覆盖窗口内全部可读取的 PR。将已合并和仍在等待的 PR 分别统计，定位最慢的几个，并结合首轮评审等待、返工、CI 和合并等待等记录解释卡点。
- 做缺陷复盘时，在约定窗口内结合 Issue、PR 和提交查找 Bug、返工、回滚和重复修改，追溯共因。有证据支持的可预防共因沉淀为规则、已有工具可承载的自动化，或可复用的 Skill。注明记录覆盖范围和数据缺口。
